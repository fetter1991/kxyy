## 一、重构总目标（源自 Readme.md 第十章重构需求）

重构的核心方向是**从原生静态站升级为 Vue 技术栈，并实现"前端展示 / 数据管理 / 接口服务"三端分离**：

| 子目标 | 说明 |
|--------|------|
| 1. Vue 化 + 路由跳转 | 重构为 Vue 页面，实现页面跳转、数据展示、页面交互 |
| 2. 渲染与数据分离 | 保留现有页面内容，实现页面渲染与数据获取解耦 |
| 3. 管理端 | 新建管理端，用于替代 `data.js` 的"存 JS/JSON"式数据维护 |
| 4. 接口端 | 新建接口端，获取管理端录入数据，对外提供 API 供用户端调用 |

**初步架构设想**：

```
用户端（Vue 前端，原 index.html + pages/*）→ 负责展示与交互
管理端（新建 Vue 前端）                     → 数据录入与维护，替代 data.js
接口端（新建 FastAPI 后端）                 → 读取管理端数据，暴露 API 供用户端调用
```

> ⚠️ 注意：当前 `Readme.md` 中"原生优先、无后端、无构建"是**现状**描述；本宪法以 Vue 三端分离为**目标方向**（见 Readme.md 第十章）。重构期间新旧并存，见原则 8。具体技术栈落地见第七章。

## 二、核心架构约束

### 原则 1 · 双端覆盖是验收底线（不可降级）

来自 `Readme.md` 全局硬性要求，重构后依然强制：

- 任何 BUG 定位、功能、样式、交互的改动，都**必须在大屏（桌面）与小屏（移动视口）分别复现、验证**，两端均通过才算完成。
- 涉及布局/播放器/弹窗/Vue 组件的需求，须显式说明对两端的各自影响。
- 目标用户仍以**手机端访问为主**，不得为追求技术栈而牺牲移动端体验。

### 原则 2 · 渲染与数据严格分离

来自重构目标 2，是本次重构的"第一性原理"：

- 页面/组件只负责**渲染与交互**，**不得内联硬编码业务数据**。
- 所有业务数据来源统一收敛到**接口端 API**（或过渡期的 `data.js` / JSON），组件通过数据层获取。
- 数据获取逻辑集中在数据层/Service 模块，禁止在.vue 组件中直接写死 `galleryData` 等原始对象。
- 现有 `data.js` 的各数据集（`galleryData` / `musicData` / `videoAlbums` / `worksData` / `commentData`）应被接口端数据模型取代，迁移时保持字段语义一致。

### 原则 3 · 三端职责清晰、单向依赖

来自重构目标 1/3/4：

- **用户端** 只依赖 **接口端 API**，不直接读写管理端存储。
- **管理端** 只向 **接口端** 写入数据，不直接服务最终用户访问。
- **接口端** 是用户端与管理端之间唯一的数据通道。
- 禁止三端之间出现循环依赖或越权直连。

### 原则 4 · 保留现有页面内容与体验

来自重构目标 2 的"保留现有页面内容"：

- 6 个页面（相册 / 素材库 / 个人资料 / 视频 / 成长历程 / 留言）及其导航顺序、核心交互，在 Vue 化后须**功能等价**。
- 双播放器架构（页面内视频播放器 + 导航栏常驻音频播放器）作为业务特征须保留。
- 外部链接（抖音主页/直播间）、`localStorage` 留言等既有行为须延续。

## 三、编码与风格规范

### 原则 5 · 动手前先思考（不臆测）

来自 `开发规范.md` 第 1 条，重构期尤其重要：

- 明确假设；不确定就提问。
- 多种理解方式时全部列出，不替用户静默选择。
- 有更简单方案时主动提出；不清楚就停下来澄清。
- Vue 组件拆分、接口字段设计、状态管理选型等决策点，先说明权衡再动手。

### 原则 6 · 简单优先、最小改动

来自 `开发规范.md` 第 2 条：

- 用最小代码量解决问题，不做推测性功能、不为单次使用做过度抽象。
- 不添加未被要求的"灵活性/可配置性"，不为不可能发生的情况做错误处理。
- 写了 200 行却可 50 行完成 → 重写。
- 技术栈升级本身已属重大变动，组件/接口设计更应克制，避免过度工程。

### 原则 7 · 精准改动、不污染

来自 `开发规范.md` 第 3 条：

- 只动必须动的部分，匹配现有风格。
- 不"顺手改进"无关代码；不重构没出问题的东西。
- 自己改动产生的孤立 import/变量/函数必须清理；原本就存在的死代码提出来但不要删（除非要求）。
- **检验标准：每一处被修改的行都应能直接追溯到需求。**

### 原则 8 · 渐进式重构、新旧并存可控

结合 `Readme.md` 现状与重构目标，约定：

- 采用**增量迁移**而非一次性重写：可先单页/单模块 Vue 化，保持站点整体可运行。
- 过渡期内允许"Vue 用户端 + 旧 data.js"或"Vue 用户端 + 接口端"并存，但**不得让数据来源出现多套互相矛盾的真相**。
- 每次提交/PR 应可独立验证（双端可运行、核心页面可访问），不允许出现"半成品导致全站白屏"的中间态合入。
- 接口端上线前，前端可暂以 `data.js` / 本地 JSON Mock 运行；一旦接口端可用，须立即切断对本地硬编码数据的依赖（见第七章"前后端分离"硬约束）。
- 重构完成判据：管理端可录入、接口端可服务、用户端经 Vue 渲染且数据全部来自接口，原 `data.js` 硬编码数据已废弃。

## 四、工作流与质量标准

### 原则 9 · 目标驱动、可验证

来自 `开发规范.md` 第 4 条：

- 任务转化为可验证目标：
  - "加校验" → "先为非法输入写验证，再让它通过"
  - "修 Bug" → "先复现，再修复，再验证双端"
  - "重构 X" → "确保重构前后核心页面行为一致"
- 多步骤任务先列计划：`步骤 → 验证项`，循环验证直到达成。

### 原则 10 · 安全与质量红线（来自 `Readme.md` 风险清单）

重构过程必须正面处理现有 P0/P1 风险，不得因技术栈变更而掩盖：

| 等级 | 必须处理项 |
|------|-----------|
| **P0** | ① 动态 HTML 拼接 XSS：Vue 下优先用模板绑定而非 `v-html`；确需 `v-html` 须做转义/白名单 ② `data.js` 缺失白屏：接口端不可用时用户端须有降级提示，禁止整页崩溃 |
| **P1** | SPA 路由切换的事件监听/定时器必须销毁（Vue `onUnmounted`）；避免双播放器靠隐式契约互斥，改为显式状态管理 |
| **P2** | 模块级可变状态收敛为 Pinia/响应式状态；接口请求需有错误态与加载态；计时器必须 `clear` |

质量门槛（强制）：

- 所有代码合并前必须通过 **ESLint（前端）** 与 **Flake8（后端）** 检查。
- 核心功能必须有**单元测试，覆盖率不低于 80%**。
- 每次提交必须**关联一个具体的任务（Tasks）编号**。

### 原则 11 · 文档与代码同步

- 重构过程中，`Readme.md`（现状）与本文档（目标）出现分歧时，以本文档为准，并同步更新 `Readme.md` 的"技术栈/架构"章节。
- 新增的 Vue 组件、接口端点、管理端模块，应在对应文档或本文件补充说明，避免再次出现 `Readme.md` 与代码命名脱节的状况（历史教训：v1.1.7 重命名未反向同步文档）。

## 七、技术栈与落地规范（源自 `技术方案.md`）

> 本章为开发人员初步技术方案的正式并入，作为本宪法在"用什么实现"层面的**强制落地约束**。它与前文章节（原则/约束）互补：原则是"为什么与红线"，本章是"技术选型与门槛"。当本章与原则冲突时，以原则为准。

### 7.1 技术栈硬性规定

- **前端**：Vue 3 + Vite + （UI 框架，如 Element Plus）
- **后端**：Python 3.10+ + FastAPI
- **数据格式**：前后端统一使用 JSON 通信

### 7.2 核心架构约束（技术落地）

- **前后端分离**：前端不再直接读取本地 JSON 文件，所有数据必须通过后端 API 获取（对应原则 2/3）。
  - 过渡期允许本地 Mock，但接口端就绪后须切断本地硬编码依赖（对应原则 8）。
- **媒体资源**：图片、视频等静态资源仍存放在项目 `assets` 目录，通过 URL 访问（与现有资源约定一致，不破坏原则 1 双端路径）。
  - **SPA 媒体解析（M1.5 落地）**：`web/public/assets` junction 到原站 `assets/`，前端经 `useAssetUrl()` 把 `../assets/x` 统一转 `${BASE_URL}assets/x`，规避路由下相对路径错位（见 `Readme.md` §11.0.1）。
  - **原站 CSS 全量复用（M2 落地）**：将 `assets/css/style.css` 整体迁移到 `web/src/styles/original.css`，仅做资源路径替换与最小 Vue 兼容调整（`html overflow:hidden` 移除、`:root` 选择器修正），确保视觉样式、毛玻璃效果、响应式与原站一致。后续 T13 再按设计系统拆分抽象。
- **API 设计**：必须遵循 RESTful 风格。

> **⚠️ 当前版本执行重点（用户 2026-08-06 拍板，临时覆盖优先级）**：**页面样式还原 > 接口数据实现**。
> 本轮优先让页面视觉还原（复用原站 `assets/css/style.css` 深色玻璃拟态）、媒体可加载、双端可测；接口持久化（T07）顺延至样式稳定。播放器（T16）暂缓，Layout 已预留 `#navMusicBtn` 挂载位。该重点不违反宪法原则，系执行序调整（原则 5 先思考 / 原则 6 等价优先）。

### 7.3 代码与风格规范（技术落地）

- 前端使用 `<script setup>` 语法。
- 后端使用 Pydantic 模型进行数据验证。
- 所有 API 必须有详细的 Swagger/OpenAPI 文档注释。

### 7.4 工作流与质量标准（技术落地）

- 所有代码合并前必须通过 **ESLint（前端）** 和 **Flake8（后端）** 检查。
- 核心功能必须有**单元测试，覆盖率不低于 80%**。
- 每次提交必须**关联一个具体的任务（Tasks）编号**。
